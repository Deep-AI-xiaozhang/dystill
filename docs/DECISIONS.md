# 决策记录（DECISIONS）

> 这份文件是**「唯一状态真相源」**：记"现在是什么行为"和"为什么"，不记"打算做什么"（那是 ROADMAP）。
> 有意偏离常见做法的地方，必须在这里留一条并写明依据——
> 否则下次看代码的人（包括三个月后的你）会以为"这是没做完"，进而推翻一个本来是对的决定。

## 记录格式

每条写四样：**决定 / 与哪份文档不一致 / 依据 / 什么时候该重新考虑**。

---

## D1 · ❌ 不一致默认不自动改写笔记

- **决定**：核对默认只出报告（`check.json` + `check.md` + 笔记顶部徽章），
  笔记正文一个字都不改；想把 ❌ 的句子按证据改回笔记，必须显式加 `dystill check --rewrite`。
- **不一致**：设计上原本写的是「❌ 不一致（自动重写）」。
- **依据**：
  1. 本产品的承诺是「笔记会自己坦白」。**用户要能看到 AI 原本错在哪**，才可能相信它核过的部分；
     静默改写抹掉的恰恰是这份可信度。
  2. 改写本身是**又一次生成**（模型给的 fix 建议），会引入新错误；改完还得再核一遍才敢信——
     而再核又可能再改，判定不稳定。
  3. `--rewrite` 只在"原句能在笔记里逐字匹配"时才动手，避免模糊替换静默篡改。
- **什么时候重新考虑**：如果真有人反馈"我就是要一键修好，不看报告"（而不是"配置麻烦"），再考虑把它设为默认。
  注意区分这两种反馈——后者说明痛点是安装，不是改写。

## D2 · 长笔记超上限时「按章节轮转取样」，不自动降级为 fast 模式

- **决定**：候选声明超过上限（fast 40 / standard 120，可用 `pipeline.check_max_claims` 调）时，
  按章节轮转取样，保证每一节都有代表进入核对；截断事实**写进报告**的跳过清单。
- **不一致**：无（设计文档没规定截断策略，是本轮实测补的）。
- **依据**：实测真实笔记 164 条候选 / 上限 120，`claims[:120]` 的 head 截断会让
  「数据基准（20 条）/ 对你的启发（17 条）/ 转化链路（5 条）」**覆盖数全是 0**——
  用户看到"已核对 120 条"根本不知道后半篇连看都没看。轮转后覆盖章节 6 → 9。
  另外：自动降级成 fast 会**静默改变核对强度**（fast 不核步骤类声明），
  与 modes.py 里"未知模式直接报错而不是悄悄退回默认"是同一条原则——降级必须显式。
- **什么时候重新考虑**：若 L1 能把候选压到上限以内（例如笔记模板稳定后句子数下降），这条自然失效，不用动。

## D3 · 第三方下载层不进仓库，用脚本拉取

- **决定**：`external/douyin-downloader`（MIT，jiji262）在 `.gitignore` 里，用
  `python scripts/setup_downloader.py` 拉取（默认走 gh-proxy 加速）；脚本**不自动改 config.yaml**。
- **不一致**：无（设计上只说"保留 jiji262 版权声明"，没说怎么分发）。
- **依据**：
  1. 它是别人的项目且自带 `.git`，vendor 进来会让 license 归属与贡献者预期变乱；
  2. 它的更新跟着抖音签名算法走，vendor 意味着"平台一变，更新责任变成我们的"；
  3. 但"全新机器按 README 30 分钟跑通"（M3 验收）又需要一键化 → 脚本 + 打印配置片段是折中。
  4. 不自动改 `config.yaml`：那里存着 API key。凭据文件永远由人自己动（同 `.gitignore` 的"凭据红线"）。
- **什么时候重新考虑**：如果上游停更或不再维护，就得评估 fork 自维护（那时才值得 vendor）。

## D4 · 判定闸门只做确定性信号，不"再问一次模型"

- **决定**：闸门（零证据 / 声明里的数字在原素材里查不到 / 深度模式覆盖度阈值；**D9 又加了第四道
  "对外商业措辞在原素材里查不到"**）都是**本地确定性计算**，
  且**只会把 ✅ 往下压**，永远不会把 ⚠️ 抬成 ✅。
- **不一致**：设计上提的是"可选 embedding 相似度做第二信号"；M1 用字面覆盖度 + 硬事实命中替代
  （设计文档 §6.4 已定 M1 不引 embedding，此处不冲突）。
- **依据**：核对工具最致命的失败是**假阳性**——用户看到 ✅ 就不再回看原片，错误就此固化。
  确定性信号不花钱、可复现、可对账；"再问一次模型"则不可复现，还可能被同一批证据再次骗过。
  **但确定性信号自己也会假阳性**（需记住的教训）：第一版硬事实检测判「通义千问3.8 Max」为"原素材里查不到"，
  翻转写才发现 `09:45` 原话是「千万三点八max」（ASR 把千问听成千万）——口播念中文数字、笔记写阿拉伯数字，
  不归一就会把有出处的事实判成编造。所以：数字比对必须先过 `num_variants`（3.8 ↔ 三点八）归一，
  且该信号**只作为闸门（把 ✅ 往下压）+ 给模型的提示**，不自己下判决。
- **什么时候重新考虑**：定 embedding 方案时（遗留问题（语义检索）），
  可用于**召回**（找同义改写的证据），但仍不能用于**判定**。

## D5 · 「片段里没找到」不许判成「原视频没有」

- **决定**：`mismatch` 只用于**证据明确与声明矛盾**（数字不符、说法相反、评级/结论不符）。
  "在我看到的片段里没找到"一律判 `doubt`。另外两条口径：
  ① 转写是 ASR 产物，同音错字按**音近**处理（codes↔Codex、质普↔ZCode、千万↔通义千问、occa↔Orca）；
  ② 笔记声明多是**概括**，换了说法但证据支持 → 判 ok，不因"没逐字出现"判存疑。
- **不一致**：设计上"❌不一致"原本定义得比较宽（"笔记写得对不上原片"），本条把边界收紧到"明确矛盾"。
- **依据**：首轮 M1 基准（40 条）里，人工判 ok 的 36 条中引擎判 mismatch 6 / doubt 16。
  逐条翻原文后确认**不是证据没送到**——离线召回体检（`scripts/recall_audit.py`，零成本）显示：
  人工判 ok 组的交付证据覆盖度均值 0.53，非 ok 组 0.26，两组分离干净，只有 5 条真的覆盖不足。
  所以问题在**判定口径**：模型把"我的片段里没有"说成了"原视频没有"，又把 ASR 错字当成"名称写错"。
  对一个核对工具来说，**假 ❌ 的伤害是让人不再相信 ❌ 标记**，和假 ✅ 是两种不同的败法。
- **什么时候重新考虑**：若"原视频确实没提"这类**假阴性**（该 ❌ 判成 ⚠️）开始变多，
  说明口径放得太松——那时应启用深度模式的覆盖度阈值，而不是把它整体收紧回去。

## D6 · 召回宽度、钉事实与邻域补全（L2）

- **决定**：L2 默认 `top_k=4` + `pin=True`（含声明全部硬事实的段必须入选）+ `window=2`
  （选中最高分段后纳入其前后各 2 段再合并）。
- **依据**：笔记的要点常由**好几句话拼成**（"设置里找到电脑控制→勾选→授权屏幕录制权限"
  跨转写 `04:16/04:24/04:28` 三行），这类声明对任何单段的覆盖度都不高，按纯覆盖度选段会一段都选不中。
  实测（同一份 40 条基准）：交付覆盖度均值 0.527 → 0.547，覆盖不足的声明 6 → 5 条。
  **效果有限，但这几条正是最容易被误判的**，且代价只有提示词多几百字。
- **什么时候重新考虑**：若提示词长度成为瓶颈（长笔记 120 条 × 证据），
  退回到"只保留钉住的段 + 邻域"，把 top_k 让给别处。

## D7 · 画面理解「一帧一次请求」，不把全部帧塞进一次请求

- **决定**：`providers/vision.py` 默认 `batch_size=1`（每帧一次调用）+ 2 路并发 +
  **单帧失败只标记该帧**；`pipeline.vlm_batch_frames` 可调大，但默认值和注释都指向"别调大"。
  每条画面证据带 `--- 第 N 张图（文件名） ---` 标记，证据层据此把画面片段映射回时间戳。
- **不一致**：初版新实现是 `describe_images(frames, prompt, ...)`——把全部抽帧（默认上限 48）
  塞进一个请求。老工具（`vision_tool.py` + `distill.step_vision`）是逐帧调用，本条回到老工具形态。
- **依据**（2026-09-17 实测，全部用项目真实抽帧）：
  1. **截断**：智谱免费 `glm-4v-flash` 的 max_tokens 硬上限是 `[1,1024]`，多图×3 就撞顶
     （多图 2229 字 vs 单图 281 字——看上去多图更多，但那是**三帧合起来的量**，
     单帧信息量反而更少，且再多的帧会被硬切）。
  2. **稀释**：同一模型（Qwen3.5-35B-A3B）单帧时 6 个画面文字锚点命中 5 个，
     多图×8 时只命中 2 个——一条请求里的注意力被摊薄了。
  3. **一损俱损**：整条画面维度只有一次调用机会，失败就全丢；逐帧只丢那一帧。
     老工具正是靠"逐帧 + 帧级 md5 缓存 + 3 次退避重试"跑过 200+ 条视频。
  4. 代价可接受：18 帧 × 2 路并发在实测里是分钟级，且失败帧不影响其余帧。
- **顺手确立的两条事实**（推翻本会话早前写下的错误结论，别再按旧笔记选模型）：
  - **DeepSeek-V4.1-Flash 能读图**：单图 8.4s / 518 字、多图×8 24.7s / 3019 字，
    画面文字锚点全部命中——它同时还是判定最快的文本模型（1.3s），值得按"一个模型全包"重新量。
  - **GLM-5.3-Flash 在魔搭通道上带图拿不到结果**（单图 120.4s 返回 SSE 空壳、`prompt_tokens=0`；
    多图 1.2s 返回异步壳），但这**不等于它不是多模态**：智谱官方 API 认得 `glm-5.3-flash`
    （报的是"余额不足"而非模型不存在）。选模型要分清"模型能力"与"某条通道的接入形态"。
  - `max_tokens` 因此提升为 `ProviderConfig` 字段：把"这家的怪癖"写在配置里，
    而不是让每个调用方记住（glm-4v-flash 的 1024 就是这么踩出来的）。
- **什么时候重新考虑**：若某家模型明确支持大批量图片且不截断（例如专门的长上下文 VL 接口），
  可把该 provider 单独配 `vlm_batch_frames>1`；届时必须重跑"锚点命中率"对比，不能只看耗时。

## D8 · 供应商按实测排序，不按"模型新旧"（当前主力：Agnes）

- **决定**：默认配置顺序 = `agnes-2.5-flash` → `agnes-3.0-flash` → 魔搭 Qwen3.5-35B-A3B → 商汤。
  注意 **更新的一代（3.0）排在旧一代（2.5）之后**，这是实测结果，不是笔误。
- **依据**（同一批 6 张真实抽帧、同一提示词、2 路并发，2026-09-17）：

  | 供应商 | 模型 | 每帧耗时 | 备注 |
  |---|---|---|---|
  | agnes-2.5 | agnes-2.5-flash | **2.7s** | 最快；判定 57.5–65%、假阳性 1 |
  | modelscope | Qwen3.5-35B-A3B | 5.7s | 判定阶段 **5 批里 4 批 180s 超时**，只能兜底 |
  | sensenova | sensenova-6.8-flash-lite | 19.2s | 思考链长（reasoning_tokens 2000+） |
  | agnes | agnes-3.0-flash | 28.4s | 比同家旧代慢 10 倍；判定 53.1%（32/40） |

  命名提醒：模型叫 **`agnes-3.0-flash`**，写 `agnes-3-flash` 会 `model_not_found`。
- **两条方法论收获（比选型本身更重要）**：
  1. **`temperature=0` 不等于可复现**：agnes-2.5-flash 同一份基准跑两次得 65.0% 与 57.5%，
     差 7.5pp。所以**单次跑的基准数字只能当区间看**，要下结论得重复跑或扩大样本。
     这也解释了此前"42.5% vs 62.5%"这类跨次比较为什么不可靠。
  2. **假阳性必须定位到条目，不能只看计数**：本次唯一那条假阳性是
     「可基于 Computer Use 功能提供竞品调研服务…」——人工判 `doubt`（笔记把视频里"我自己用的三个场景"
     写成了"对外提供服务"），模型判 `ok`（因为"Computer Use / 竞品调研"确实都在原素材里）。
     **硬事实全对、推理方向被改了**，逐条证据匹配看不出来。这是产品要补的一类闸门，
     记为待办（见下），不能靠"换个模型"解决。
- **什么时候重新考虑**：① 出现比 Agnes 更快且判定假阳性 = 0 的免费通道；
  ② Agnes 免费额度收紧或改成收费。重选时必须用 `scripts/vlm_probe.py`（读图形态）
  ＋ `scripts/model_pick.py`（判定质量）+ `--dump`（定位假阳性）三件套跑一遍，别只看速度。
- **待办（本次暴露，未解决）**：补一类"推理性改写"闸门——
  笔记把「我用的功能」升级成「对外提供的服务/产品」时，即便硬事实都在源里也应判存疑。

## D9 · 「推理性改写」：提示词纪律 + 第四道确定性闸门

- **决定**：两层都做，但分工明确——
  1. **提示词纪律**（主）：L3 提示词新增一条，明确告诉模型这类升格（提供服务/对外/客户/接单/变现）
     应判 `doubt`，理由是"原素材只说了作者自己在用"。**这是主力**，因为它能理解上下文。
  2. **第四道确定性闸门**（兜底）：`business_leap()` 词表命中且**整条原素材里一个都没有** → 不许判 `ok`。
     它与前三道闸同一条纪律：只把 ✅ 往下压，绝不把 ⚠️ 抬成 ✅。
- **依据**：
  - **词表的精度是量出来的，不是想出来的**：40 条基准里**只有 1 条**命中词表，而它正是那条唯一假阳性；
    其余 39 条零触发 —— 精度 100%、代价 0。
  - 词表刻意**不收**「提供/交付/支持」这类日常动词（"提供图形界面"会被误伤成存疑），
    也不收「收费/付费」（它们在原素材里以别的意思出现过："操作我已经下载了这款收费的阅读器"、
    "用户付费的点"）。宁可漏，不可误伤——误伤会让用户不再相信 ⚠️。
  - 实测（agnes-2.5-flash / fast / 40 条）：**假阳性 1 → 0**，一致率 60.0% → **70.0%**（28/40）。
- **⚠️ 归因要说清（别把功劳记错）**：这一轮假阳性消失，**是提示词纪律起的作用，不是闸门出手**——
  该条声明的判定理由是模型自己写的"原素材只说了作者'我经常用 Computer Use 做以下 3 个场景'，
  没有提到'提供…服务'、'定制服务'等对外商业行为"，不是闸门的文案。
  闸门这次是**未被触发的兜底**（其确定性行为由单测锁定）。这一点很重要：说明这类语义跳跃
  **模型本来就认得，只是先前没人告诉它要去认**——那么后续同类问题应优先改提示词，而不是堆闸门。
- **同时暴露的下一个问题（下一步）**：剩下的 12 条分歧里，
  **有 5 条是"人工判 ok、引擎判 mismatch"**，逐条看证据后**其中至少 2 条引擎可能是对的**
  （「AI 操作时用户无法操作自己的鼠标」原素材说"有自己的鼠标、不影响正常操作"；
  「Codex 体验最好」原素材结论是 Claude Code）。也就是说**该复核的是人工标注**，不是引擎。
  在没复核之前，70% 这个数字的分母本身是不可靠的。
- **什么时候重新考虑**：若词表在别的题材上开始误伤（命中但人看是有出处的），
  就把它降级为"只进提示词、不做闸门"，而不是继续加词。

## D10 · 修掉 4 个真 bug，并承认两件事：L2 的天花板 + 单次测量不可复现

**背景**：复核 5 条"人判 ok、引擎判 ❌"时发现**全是我对、引擎错**（我先前说"至少 2 条引擎可能对"
是错的——那时我只看了引擎给的片段，没看片段属于哪款工具）。逐条回原文定位到根因，修掉 4 个真 bug：

1. **帧号钉住被字数预算裁掉**（钉了等于没钉）：`pin` 只把段放进候选集，
   但候选集随后按 `(-fact_hit, -score)` 排序裁剪，声明点名的帧往往 fact_hit=0、score 低，
   一超预算就被裁。→ 新增 `Evidence.pinned`，钉住的段**豁免预算**，
   并设保底 `PIN_MIN_CHARS=1500`（预算被调小时也不许裁）。
2. **栏目名在 L1 被剥掉**：笔记 `- **测试任务**：找到下载目标栏并上传 pio 文件` 送进 L3 时只剩后半句，
   模型读成"断言上传成功"，对着"上传失败"的原素材判 ❌。
   → `Claim.context`（栏目名）参与**检索**与**判定渲染**，提示词加纪律 9。
   实测：该条从 ❌ 变 ✅，理由是"说明**测试任务**确实是找到并上传 pio 文件"——模型真的用上了栏目名。
3. **模型漏返条目没有补问**：`verifier` 把"模型未返回该条判定"直接记 ⚠️ 存疑。
   但这是**机械失败，不是判断**，白丢一条本该 ✅ 的。→ 单独再问一次那几条（不重跑整批）。
4. **帧号声明没被用来选画面证据**：声明写"第11-13张"、检索却喂**第 8 张**（别的工具界面）。
   → `frame_refs()` 解析"第 N 张/N-M 张"，那几帧**硬性入选**。

**同时确立两件不该被粉饰的事**：

- **L2 字面覆盖度过不了"同主题不同工具"这一关（设计天花板）**：实测测过——
  把栏目名加进查询，目标段在转写里的排名只从第 12 名挪到第 9 名（**加词会加大分母、稀释每段得分**），
  而 Codex 那几段因为和声明共享"鼠标/操作/自己"这类通用词稳居前列。
  也就是说：**在"多款工具做同一件事"的视频里，字面检索几乎必然把 A 工具的证据喂给讲 B 工具的声明**。
  这不是调参能解决的，正解是实体对齐或 embedding 语义检索（遗留问题（语义检索），M1 有意不引）。
  **当前对策只能是提示词纪律 10**（证据讲的是另一款工具 → 判 doubt 而不是 mismatch），
  把"编造的错误"降级成"诚实的存疑"。
- **⚠️ 单次测量在条目级不可复现**：同一份基准连续两次跑（代码只差"补问 + ASR 别名"），
  聚合一致率都是 65.0%，但 ❌ 的条数 **0 vs 5**、**假 ❌ 的条目集合几乎完全不同**。
  结论：**聚合数字只能当区间看，条目级的"某条修好了"不能凭一次跑下结论**；
  要判断一个改动是否真的有效，必须重复跑或直接查该条的判定理由（后者免费且确定）。
  这也是"扩样本到 50 条"之外、更该先做的一件事：**给验收定义"重复 N 次取区间"的口径**。

- **什么时候重新考虑**：引入 embedding 召回时（可用于**召回**，仍不能用于**判定**，见 D4）。

## D11 · 抖音单视频下载已被平台封堵（2026-09-14 起），本项目的应对是「本地文件优先」

- **事实（实测，2026-09-17）**：抖音对**单个视频**接口 `aweme/detail` 启用了 Argus 风控，
  非浏览器请求一律返回空详情。放行所需的 `x-secsdk-web-signature` **只能由抖音网页内的 SDK 生成**，
  CLI 直连无法带上。第三方下载器（jiji262/douyin-downloader）自己的 README 也写明
  「单个视频 / 图文在 CLI 中**无法使用**」，桌面版客户端靠内置登录窗口代发请求才不受影响。
- **排除过的路（别再重复试）**：
  - 游客 ttwid → 被拒
  - 完整登录态 cookie（含 sessionid / sid_guard / odin_tt / __ac_signature）→ 仍被拒
    （说明**不是 cookie 失效**，别在这上面耗）
  - `yt-dlp` 的 Douyin 提取器 → 撞同一堵墙（它源码里的报错就是"Fresh cookies … are needed"）
  - 移动端分享页 `iesdouyin.com/share/video/<id>` → 200 但页面里只有 AB 参数，**没有播放地址**
- **决定**：把"下载"这一步定位成**可替换的前置步骤**，而不是产品的核心承诺。产品承诺是
  「本地素材 → 可信笔记」，素材怎么来交给用户。具体做法：
  1. 失败时**不再报"cookie 可能失效"**（误导人去折腾 cookie），直接输出可行动提示：
     先装浏览器兜底（见 D13），再走本地文件 `dystill run <文件路径>`，或换源（B 站走 yt-dlp，本项目已支持）
  2. README 的定位不改（仍支持抖音链接），但把"平台可能封"写进诚实边界
- ~~什么时候重新考虑~~ → **已被重新考虑（2026-09-17）**：浏览器兜底已实测验证可用并落地，见 **D13**。
  本条的"本地文件优先"仍然成立——那是产品定位（素材获取不承诺），但"抖音链接不能用"已不再成立。


## D13 · 抖音风控先回真浏览器兜底（2026-09-17，推翻 D11 的"浏览器未验证"）

- **事实（实测，2026-09-17）**：D11 当时说"浏览器兜底未验证，需 playwright + 有头浏览器"。
  同日早期版本用 **headless** Chromium 实测：同一 IP 同一时刻，
  下载器 API 3 次全 403（duration_ms=31~62 / risk_control=True），而 headless 浏览器打开
  视频页能拦到 `aweme/detail` 的 **HTTP 200 / status_code=0 / play_addr×3**，15s 下完 8508 KB。
  下线记录：EXECUTION_LOG v85 → 16:35/16:43/17:28 三次全 ❌，18:03 修复后 ✅（下载 62s）。
- **根因**：403 在十几~几十毫秒内返回且带 risk_control = 抖音边缘 WAF 按**纯 HTTP 客户端指纹**
  直接拒，**不是 cookie 失效、不是 IP 被封**。退避重试救不了指纹型 403（三次同速被拒），
  回真实浏览器（带完整 JS 环境、可算合规签名）才是正解。
- **决定（本项目怎么落地）**：
  1. **编排顺序**：API 首次命中风控 → **立即切真浏览器兜底**（不退避等待）→ 浏览器失败才
     30s/90s 退避重试 API → 全失败才抛错。
  2. **实现**：新增 `core/browser_download.py`（Playwright headless Chromium 拦 detail 响应 →
     取 `video.play_addr.url_list` → 用页面上下文自己的 request 下 CDN → 按
     `{date}_{title}_{id}.mp4` 落盘）；`core/download.py` 用 `RiskControlDetected` 把
     瞬时风控与确定性失败（图文帖/配置错）分开，只对风控重试/兜底。
  3. **依赖取舍**：playwright **走可选依赖** `dystill[douyin-browser]`，不做硬依赖——
     只处理抖音链接时需要；没装自动退回 API 重试，本地文件 / B 站路径零影响。
  4. **cookie 体检**：下载前体检下载器真正读的 `.cookies.json`（sessionid/ttwid/msToken）；
     这只是提示，不做门禁——实测 cookie 完整也会被风控挡（指纹问题）。
- **验证**：① 本地 mock 服务器模拟抖音页（页内 JS 发 detail 请求 + /play 返回 ftyp 头 mp4），
  `download_via_browser` 端到端通过：拦到 detail → 取 play_addr → 下 CDN → 落盘
  `2026-09-17_冒烟测试视频标题 带特殊字符_7391234567890123456.mp4`（ftyp 校验过）。
  单元测试 22 个新增用例全绿 + 全量 143 通过。
  ② **真实链接实测（2026-09-17 晚）**：一条真实分享短链 → 浏览器兜底直接成功，
  12MB 视频落盘（`{date}_{title}_{id}.mp4`，本次标题含特殊字符），
  标题/aweme_id 解析正确。随后完整流水线跑通：转写→切帧（4帧）→VLM（4/4）→笔记，112s 全绿，
  产物 `transcript.txt / vlm.txt / note.md / frames/ / meta.json` 齐备，笔记内容与转写对应。
- **什么时候重新考虑**：抖音网页端也上强验证（验证码/登录墙）时，浏览器兜底会退化；
  届时候选路径：带登录态的浏览器 context、或彻底退回"本地文件优先"定位。




## D12 · 数字命中必须带边界；帧号不是事实数字（2026-09-17 全面检查修掉的两个真 bug）

- **决定**：
  1. `hard_miss` 的数字命中从**子串匹配**改为**边界匹配**（`_number_in_source`）：
     声明里的 200 不能再从原素材里的 2000 / 1200 里"找到出处"。
  2. `hard_facts` 提数字前先剥掉「第 N 张/幅/帧」帧号（含 `第11-13张` 区间写法）。
- **不一致**：无（这两处是 bug 修复，不是设计偏离）。
- **依据**：
  1. 子串匹配会让「编造数字」这道闸（D4）形同虚设：口播说 2000、笔记写 200，
     边界匹配下 200 查不到 → 判存疑；子串匹配下 200 in 2000 → 假 ✅。
     数字是最硬的证据点（ASR 听错名字但很少听错数字），这道闸漏了等于没核。
  2. 画面小节常写「第 3 张图显示…」，那个 3 是画面序号不是声明内容，
     被当成"原素材里查不到的数字"会把本该 ✅ 的声明压成 ⚠️——假 ❌ 的另一来源（D10 修了一半的残留）。
- **什么时候重新考虑**：若未来引入真正的数值归一（如"200"与"0.2k"等价），
  边界匹配仍是前提——先有正确边界，再做等价变换，顺序不能反。

## D33 · L2 诊断反转：送达已到上界，过度存疑的真因是"词汇墙"；拼音兜底证伪（2026-10-05）

## D36 · 治假 ❌ 的提示词加固被实测否决：修 1 条、坏 10 条（2026-10-14）

- **动机**：抽检新视频时抓到一条假 ❌（声明「示例规则把『替我回复邮件』设为『先询问』」，
  证据里明明有口播"让他先询问我"支持它，模型却因为同批证据里另一处画面文字"自动审核"
  判了 mismatch）。据此给判定提示词加了纪律 11：判 mismatch 必须写出证据里冲突的那句话，
  写不出就改判 doubt。
- **验证方法（定点回放 + 同日对照，按 D16 纪律）**：取 Grok Bot 视频的 130 条声明与
  **存档证据**，用新提示词重判一遍（130 条 / 26 批 / 1890s），与存档判定对比；再把翻转的
  13 条用**旧提示词当天重判一遍**（3 批 / 128s）作对照，把「提示词效果」与「模型漂移」分开。
- **结果**：
  | | 存档(旧提示词) | 新提示词 | 旧提示词(同日) |
  |---|---|---|---|
  | C49（假 ❌） | mismatch | doubt | ok |
  | 10 条（C11~C15/C33/C83~C85/C126） | ok | doubt | ok |
  | C82 | ok | doubt | doubt（漂移） |
  分布：旧 `ok96/doubt33/mismatch1` → 新 `ok86/doubt44/mismatch0`。
- **结论**：**净亏**——修好 1 条假 ❌，却把 10 条本该 ✅ 的压成 ⚠️（真 ❌ 换假 ⚠️，用户
  拿到的是更难用的报告）。**已回滚**，`verifier.py` 恢复原提示词。
- **方法论收获**：不加同日对照的话，这 11 条翻转会被整笔记成"提示词效果"（实际 10 条是效果、
  1 条是漂移）；反过来，如果只看"假 ❌ 修好了"就收工，会把一个更差的规则上线。
  **判定的"保守化"不是免费的**：把判不准的都推给 doubt，会让报告失去信息量。
- **状态**：假 ❌ 暂不治。若要重开，方向应是"提高 L2 证据交付质量"（让模型看到真正相关、
  且不掺无关片段的证据），而不是继续在判定提示词上加约束。

## D37 · L2 证据交付诊断：噪声确实多，但"减少证据"与"增加证据"都测不出效果（2026-10-14）

- **零成本诊断（读存档 check.json，925 段证据）**：平均每条声明交付 7.1 段 / 1818 字符，
  其中 **34% 的段落是低分（score<0.1，基本无关）**；15/130 条声明的证据里一半以上是无关内容。
  噪声来源已定位：`window`（锚点前后各取 2 段，不看相关性）贡献约 10% 字符。
- **切段实验（同批 25 条、同提示词同模型，只改证据集合）**：
  | 条件 | 证据量 | 结果 |
  |---|---|---|
  | A 不过滤 | 38583 字符 | 20 ok / 4 doubt / 1 mismatch |
  | B 过滤 score<0.05 | 31813（−18%） | 18 ok / 7 doubt / 0 mismatch |
  | C 过滤 score<0.1 | 20133（−48%） | 15 ok / 10 doubt / 0 mismatch |
  **过滤越狠、存疑越多**（与 D36 同一规律：削减证据=把拿不准的推给 ⚠️）。

## D38 · 转写精度显式化：CUDA 上禁止落回 int8_float16（2026-10-14）

- **问题**：`FasterWhisperSTT` 原来写 `WhisperModel(model, device="auto", compute_type="auto")`。
  实测（本机 RTX 3050，`ctranslate2.get_cuda_device_count()==1`）**auto 解析结果是
  `cuda / int8_float16`** —— 正是被证明会静默丢内容的那档量化。
- **证据（早期版本同音频对照，2026-10-14）**：646s 中文口播音频，
  `int8_float16` → 3317 字符（**15~44s 整段 29 秒内容消失**），`float16` → 3484 字符（完整）；
  速度只差 8%（15.0s vs 16.6s）。转写文件不报错、字数看着正常、无任何告警。
- **为什么对本项目更致命**：核对引擎以转写为唯一文本证据源。转写静默丢字 ⇒ 笔记里**正确**的
  内容被判「找不到出处」⇒ **假 ❌ / 假 ⚠️**。也就是说这个 bug 会**直接污染核对指标**，
  而现有全部基准数字（含留出集）都建立在这些转写之上。这是评估 FP 前必须先排除的隐藏变量。
- **本机存量体检（零成本）**：对 `data/` 下 25 条已存转写算「字/秒」（中文正常 3~7），
  **0/25 低于 2.0**（最低 3.14）——说明该坑在本机数据上**尚未发作**，属运气而非设计。
  但已存转写不重跑就不会暴露，故不作为「无问题」的证据。
- **动作**（`core/stt.py` + `config.py` + `cli.py` + 两份 `config.example.yaml`）：
  1. 新增纯函数 `resolve_device_compute(device, compute_type, cuda_available)`：
     `auto` 解析为 `cuda/float16` 或 `cpu/int8`，**不再交给 ctranslate2 的 auto**；
     显式传 `compute_type` 时原样使用（留显存不足的降级逃生口）。
  2. `STTConfig` 新增 `device`（默认 `auto`）与 `compute_type`（默认空=自动解析）两个可配项。
  3. `transcribe_raw` 显式加 `condition_on_previous_text=False`——开着它模型会顺着上文「编」，
     是复读/幻觉的主要来源；本产品的核心承诺是「不瞎编」，方向一致。
  4. 新增 `tests/test_stt.py` 5 条（含「CUDA 不许落回 int8_float16」的回归断言），全套 187 通过。
- **诚实边界**：第 3 项（`condition_on_previous_text`）与 D37 的 top_k 改动同性质——
  **方向正确但当前样本量测不出效果**，不宣称改进。第 1 项是**确定性缺陷修复**，
  有同音频 A/B 实测支撑，不是方向性判断。
- **何时该重新考虑**：若将来换用非 ctranslate2 后端（如 sensevoice/funasr），
  本条精度纪律不适用，需按该后端自己的量化坑重新实测。

## D39 · 知识库汇总进工具：只做中性的「归拢与自检」，不带任何领域倾向（2026-10-14）

  | 面向特定目的的周边分析工具 | ❌ 不进 | 与"蒸馏成笔记"这个定位无关 |
- **实现（`core/kb.py` + `dystill kb`）**：
  1. **不预设分类表**。主题词 = 从**用户自己的笔记内容**统计出的跨篇高频词（标题 + 主题字段）；
     类型轴 = 笔记层自己产出的 `实操教程 / 观点认知`。换任何题材的用户都能用。
  2. 关键词统计**只取标题与主题**、不取正文——正文是模型生成的话术，模板结构词会霸榜
     （实测"视频核心""结论是"曾进榜，已加结构词过滤）。
  3. 自检只报**事实**：缺身份键 / 键格式异常 / 重复 / 空壳 / 有素材无笔记 / 失效引用 / 索引过期。
     不回答"这条笔记写得好不好"——不做价值判断是刻意的。
- **实测踩到并修掉的两个坑**：
  - **索引把自己当笔记收录**：`find_notes` 扫 `notes_dir/*.md` 会把上一次生成的
    `知识库.md` 收进去，第二次运行越滚越大。已按 `INDEX_NAME` 排除。
  - **类型字段脏值**：笔记里的类型有 `<实操教程>`（占位符尖括号没删）、`**观点认知**`
    （Markdown 加粗原样写入）等形态。索引层只能容错：`normalize_type()` 含已知类型即归位，
    不认识的值**原样保留**（不猜、不吞信息）。
  - **归组黑洞**：最初实现「每篇只归到命中的第一个主题词」，结果 24 篇里 9 篇掉进「其它」，
    等于白归。改为**多标签归组**（命中即收录，一篇可属多个主题），每个主题组都是完整的；
    代价是跨主题笔记重复出现，对索引可接受。
  - **英文关键词大小写**：统计时英文已转小写，标题里是 `AI`，`"ai" in "热门 AI Agent"` 为 False
    → 命中率暴跌（实测 ai 只归到 2 篇，修后 10 篇）。匹配一律走 `.lower()`。
  - **切词碎片**：2~4 字滑窗会切出 `视频的` `与使用` 这类虚词边界的碎片。加虚词首尾过滤
    （`_PARTICLE`）——纯字符层面的规则，与领域无关。
- **数据清理（同批）**：`data/aweme_7678251600959376681/` 下发现两条**不属于本工具的旧产物**
  （`note.md` 与一条 `note-旧营销版备份.md`：用的是一套早于本工具的笔记模板，key 为空、
  标题写成"视频"）。已**移出项目**至 `_隔离备份\`（移出而非删除，内容可回收），
  随后按用户要求删除整条记录目录。现 `data/` 下 24 条记录，`dystill kb --check` 全绿。
- **未做（有意）**：不自动改笔记正文、不生成"推荐看哪几篇"这类价值排序、不引入 embedding。
- **何时该重新考虑**：若将来要做"跨笔记的知识图谱/语义检索"，需要引入向量库——那会带来
  新的依赖与隐私面（笔记要发给 embedding 服务），届时另立决策，不在本次范围内。

## D45 · 发布快照策略：放弃历史、单一 orphan 提交发布（2026-10-18）

- **动机**：D46 的历史审计确认，完整 git 历史里带私有项目计划书、真实 ttwid 与个人邮箱。
  逐条重写 87 个提交的代价是全部哈希改变、文档内引用失效，还要处理 reflog 与悬挂对象；
  而收益只是"能公开开发史"——本项目暂时不需要用提交史本身对外证明什么。
- **做法**：
  1. **发布物 = 当前树的单提交快照**：从当前工作树建一个 orphan 分支，只提交一次，
     不携带任何既有历史；公开仓库从该提交开始累积后续历史。
  2. **当前树清理（本次实做）**：内部报告 `outputs/代码修复完成报告.md` 已从索引移除并
     移出工作区（内容另存到仓库外 `D:\自制开源工具\dystill-internal-report-backup-20261018.md`），
     不进入发布快照；`.gitignore` 补齐三处实际缺口——
     ① `outputs/` 此前未被忽略，内部报告因此被跟踪；② `*_key.txt` / `*_token.txt`
     凭据后缀未覆盖；③ 计划书忽略规则写成「蒸馏工坊项目计划书*.md」，而历史文件名是
     「蒸馏功坊项目计划书…」（一字之差），规则从未命中。
  3. 移除 `.gitignore` 里对留出集 CSV 的放行例外，`bench/*` 继续整体忽略。该 CSV 从未

- **结论**：公开仓库只有一个"当前状态"提交，不含任何开发历史；完整开发史仅存于本机
  bundle（D46）。代价是公开侧没有可追溯的提交史，issue/PR 中不能引用旧 commit——
  接受，因为本项目的可信度由留出集与实测数字支撑，不由提交史支撑。
- **何时该重新考虑**：若将来要接受外部贡献、以 git 历史作为协作主线，应从该快照提交

## D46 · 历史泄漏审计：结论与处置（2026-10-18）

- **动机**：发布前必须回答"旧历史里到底有什么"。只扫当前工作区不够——被删除的文件仍
  留在历史对象里；也不能把"文件名没扫到"当成没泄漏。
- **方法**：`git log --all` 逐提交统计；`git log -S <字符串>` 回溯敏感值的引入与移除；
  `git ls-files` 对照当前树；核对 `git remote -v` 与 `git tag`。
- **审计结论（逐项实测）**：
  1. **私有项目计划书**：`蒸馏功坊项目计划书-v2备份-20260831.md` 在 2026-09-17 的初始
     提交入库，后在 `9732476`、`da9595f` 两次提交中移出索引并加入 `.gitignore`；但文件
     内容（含私有流水线路径）仍存在于历史对象，可取回。
  2. **真实 ttwid**：`downloader.base.yml` 在初始提交里含一条真实登录态 ttwid，后续提交
     将其移除、改为从 `cache/douyin_cookies.txt` 读取；该值仍留在历史里。
  3. **个人邮箱**：87 个提交的 author/committer 全部指向同一个个人邮箱（此处不复述地址）。
  4. **留出集 CSV 更正**：`git log --all -- bench/claims_holdout1.csv` 为空——该文件
     **从未进入 git**。D30 记载的"放行入库"只是 `.gitignore` 规则，没有实际提交；当前
     工作区也没有这个文件（副本已丢失）。D27/D30 的留出集数字与结论不受影响，但"标签
     已随仓库保存"这一前提不成立。
- **处置**：
  1. **不重写历史**：仓库 `git remote -v` 为空、`git tag` 为空，没有已发布的历史需要擦除；
     重写 87 个提交会改变全部哈希、破坏 DECISIONS 内的引用，风险大于收益。
  2. **发布走单提交快照**：见 D45，发布物不携带上述任何历史对象。
  3. **完整历史另存本地 bundle**：`D:\自制开源工具\dystill-history-backup-20261018-1647.bundle`
     （`git bundle verify` 通过：含 master / release-public / improve-verifier 与 HEAD
     共 4 个 ref，完整历史，约 500 KB）。该文件**不随仓库发布、不上传**，仅作本机
     回滚与追溯用。
- **结论**：公开物从"历史不可控"收敛为"当前树可枚举"；遗留风险只剩"当前树是否还有
  敏感内容"，已由 D45 的清理与 ROADMAP F4 的发布检查清单覆盖。
- **何时该重新考虑**：若 bundle 要交给第三方托管或归档，先确认接收方与访问控制；若将来
  确要公开历史，必须先对计划书、ttwid、邮箱做 `git filter-repo` 级清理并重写全部哈希，
  不能直接把 bundle 推成公开仓库。
